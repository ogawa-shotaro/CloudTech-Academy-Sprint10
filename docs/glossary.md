# プロジェクト用語集 (Glossary)

## 概要

このドキュメントは、本プロジェクト(売上レポート自動配信ワークフロー)で使用する用語を定義する。とくにAWSサービス固有の用語は、コンソールで構築する際に迷わないよう「本プロジェクトでの用途」を必ず記載している。

**更新日**: 2026-09-14

## ドメイン用語

### 売上レポート自動配信ワークフロー

**定義**: 経理担当者が毎月手作業で行っていた売上データの集計・レポート作成・メール送付を、AWS上のサーバーレス構成で自動化する仕組み全体を指す本プロジェクトの名称。

**関連用語**: [ステートマシン](#ステートマシン-state-machine)、[レポート通知キュー](#レポート通知キュー)

### 集計(売上集計)

**定義**: S3に配置された売上CSVを読み込み、レポートの元になる数値(店舗別合計など、具体的な集計軸は別途定義)を算出する処理。

**関連用語**: [Lambda(売上集計)](#lambda売上集計-salesaggregatorfunction)

**使用例**: 「Lambda(売上集計)が売上CSVを読み込んで集計する」

### レポート概要

**定義**: レポート作成関数が生成する、メール本文に記載するための要約テキスト。レポートファイル本体(CSV)とは別に、SQSのメッセージに含めて渡される。

**関連用語**: [レポート通知メッセージ](#レポート通知メッセージ)

## 技術用語(AWSサービス)

### Amazon EventBridge Scheduler

**定義**: 指定した日時・スケジュール(cron式やrate式)にターゲット(Step Functions、Lambdaなど)を呼び出すマネージド型のスケジューラサービス。

**本プロジェクトでの用途**: 毎月1日9:00(JST)にStep Functionsのステートマシンを起動するトリガーとして使用する(要件2)。

**ポイント**: `ScheduleExpressionTimezone`にタイムゾーン(`Asia/Tokyo`)を直接指定できるため、UTCへの手動変換が不要。ただしこの機能自体はどのリージョンからでも使えるグローバル機能であり、リージョン選定の理由にはならない([architecture.md](./architecture.md#リージョン)参照)。

**関連ドキュメント**: [architecture.md](./architecture.md#2-eventbridge-scheduler)

### AWS Step Functions

**定義**: 複数のLambda関数やAWSサービスの呼び出しを、視覚的なステートマシンとして順序立てて実行するオーケストレーションサービス。

**本プロジェクトでの用途**: 「売上集計→レポート作成」の順に実行するワークフロー本体(要件3)。

**Standard vs Express**: Standardは実行時間が長く(最大1年)実行履歴が90日間保持され、コンソールで確認しやすい。Expressは高頻度・短時間の実行向けで低コストだが実行履歴の可視性が低い。本プロジェクトは月1回の実行なのでStandardを採用。

**関連ドキュメント**: [architecture.md](./architecture.md#3-step-functions)

### AWS Lambda

**定義**: サーバーを管理せずにコードを実行できるコンピュートサービス。リクエスト(イベント)ごとに実行され、使った分だけ課金される。

**本プロジェクトでの用途**: 売上集計・レポート作成・メール送信の3つの処理単位として使用する(要件4、5、7)。

**コールドスタート/ウォームスタート**: 初回実行(コールドスタート)は実行環境の初期化が入り遅くなる。2回目以降、実行環境が再利用される場合(ウォームスタート)は初期化がスキップされ高速。AWS SDKクライアントをモジュールスコープで初期化するのは、このウォームスタート時の再利用を活かすため([development-guidelines.md](./development-guidelines.md#aws-sdkクライアントの初期化)参照)。

**arm64(Graviton2)**: AWSが設計するArmベースCPU。x86_64より低コスト・高効率とされ、本プロジェクトのLambdaはarm64アーキテクチャを採用。

### Amazon S3(Simple Storage Service)

**定義**: オブジェクトストレージサービス。ファイル(オブジェクト)をバケット単位で保存する。

**本プロジェクトでの用途**: 売上CSVの置き場(要件1)とレポートファイルの保存先(要件5)として、それぞれ専用バケットを用意する。

**バージョニング**: 同じキーへの上書き/削除があっても、過去バージョンを復元できる機能。誤操作からの復旧のため有効化する。

**パブリックアクセスブロック**: バケットやオブジェクトが意図せずインターネットに公開されるのを防ぐ設定。本プロジェクトでは全項目を有効化する。

### Amazon SQS(Simple Queue Service)

**定義**: メッセージを一時的に保持し、非同期にコンシューマー(Lambdaなど)へ配信するマネージド型メッセージキューサービス。

**本プロジェクトでの用途**: レポート作成関数とメール送信関数を疎結合にする(要件6)ための「レポート通知キュー」と、失敗したメッセージの退避先である「DLQ」の2つを使用する。

**可視性タイムアウト**: メッセージが一度コンシューマーに配信されてから、他のコンシューマーに見えなくなる(=再配信されない)時間。処理中に他のLambda実行が同じメッセージを重複処理しないための仕組み。本プロジェクトでは90秒(メール送信Lambdaのタイムアウト15秒の6倍が推奨値)に設定。

**Redrive Policy / maxReceiveCount**: メッセージが指定回数(`maxReceiveCount`)受信されても正常に削除されなかった場合、自動的にDLQへ移動させる設定。要件8の「一定回数リトライ後、失敗用キューへ移動」を実現する中核機能。本プロジェクトでは`maxReceiveCount = 3`。

**関連ドキュメント**: [functional-design.md](./functional-design.md#異常フロー-メール送信失敗時のリトライとdlq退避)

### DLQ(Dead Letter Queue、デッドレターキュー)

**定義**: 正常に処理できなかったメッセージを保持するための、通常のキューとは別のキュー。メッセージを消失させず、後から調査・再処理できるようにする。

**本プロジェクトでの用途**: レポート通知キューでmaxReceiveCountを超過したメッセージの退避先(要件8)。

**関連ドキュメント**: [repository-structure.md](./repository-structure.md#runbooks-運用手順書)の`dlq-reprocessing.md`

### イベントソースマッピング(Event Source Mapping)

**定義**: SQSやDynamoDB StreamsなどのイベントソースとLambda関数を紐づけ、イベントが発生したら自動的にLambdaを呼び出す仕組み。

**本プロジェクトでの用途**: SQS(レポート通知キュー)にメッセージが入ると、Lambda(メール送信)が自動的に起動する(要件6)。

**バッチサイズ**: 1回の呼び出しでLambdaに渡すメッセージ件数。本プロジェクトでは1に設定し、1件ずつ確実に成功/失敗を判定できるようにしている。

### Amazon SES(Simple Email Service)

**定義**: AWSが提供するメール送受信サービス。

**本プロジェクトでの用途**: Lambda(メール送信)からレポート概要を含むメールを送信する(要件7)。

**サンドボックスモード**: SESの初期状態。送信元・宛先の両方が事前に検証済み(Verified Identity)である必要がある。本プロジェクトはMVPの間サンドボックスのまま運用し、任意の宛先への送信(本番アクセス)はPost-MVPの将来対応とする。

**Verified Identity(検証済みID)**: SESで送受信可能と確認されたメールアドレス/ドメイン。確認用リンクをクリックすることで検証される。

### IAM(Identity and Access Management)

**定義**: AWSリソースへのアクセス権限を管理するサービス。

**本プロジェクトでの用途**: 各Lambda・Step Functions・EventBridge Schedulerに専用の実行ロールを作成し、必要最小限の権限のみ付与する。

**最小権限の原則**: 「そのリソースが業務上必要とする最小限の権限だけを付与する」というセキュリティの基本原則。ワイルドカード(`*`)によるリソース指定を避け、対象のARNを明示的に指定することで実現する。

### IAM Identity Center(旧AWS SSO)

**定義**: 複数のAWSアカウントにまたがる人間のユーザーのサインインアクセスを管理する、IAMとは別のサービス。

**IAMとの違い**: 「IAM」はリソースに対するロール・ポリシーを管理するグローバルサービスだが、「IAM Identity Center」はそれとは全く別物で、**有効化したリージョンに固定される**という制約がある。コンソール検索で名前が似ているため混同しやすい。

**本プロジェクトでの用途**: 使用しない。Lambda実行ロールなどの作成には通常の「IAM」を使う。検索時に間違えて開いてしまった場合は、「IAM Identity Center」ではなく「IAM」を選び直す。

### DLQ Redrive(DLQの再処理)

**定義**: SQSコンソールに標準搭載されている、DLQに溜まったメッセージを元のキューへ戻す機能。

**本プロジェクトでの用途**: 異常系確認で、DLQに移動したメッセージを`sales-report-automation-notification-queue`へ再投入し、原因解消後に正常処理されることを確認する際に使用した(要件8)。

**関連ドキュメント**: [runbooks/dlq-reprocessing.md](../runbooks/dlq-reprocessing.md)

### Amazon CloudWatch Logs

**定義**: AWSサービスの実行ログを収集・保存・検索できるロギングサービス。

**本プロジェクトでの用途**: 各Lambda・Step Functionsの実行結果やエラー内容を記録し、動作確認や障害調査に使う。

## アーキテクチャ用語

### サーバーレス・イベント駆動アーキテクチャ

**定義**: サーバーの管理を必要とせず、イベント(スケジュール起動、メッセージ到着など)をきっかけに処理が実行される設計パターン。

**本プロジェクトでの適用**: EventBridge Schedulerの起動イベントを起点に、Step Functions→Lambda→SQS→Lambdaと、各コンポーネントがイベントで疎結合に連携する構成([architecture.md](./architecture.md#アーキテクチャパターン-サーバーレスイベント駆動ワークフロー)参照)。

**メリット**: サーバーの保守が不要、実行された分だけ課金される、各コンポーネントが独立して障害切り分けしやすい。

**デメリット**: コンポーネント間の連携(IAM権限、メッセージ形式など)の設定項目が増え、コンソールでの手動構築ではミスが起きやすい。

### 疎結合(Loose Coupling)

**定義**: コンポーネント同士が互いの内部実装を知らなくても連携できる設計状態。

**本プロジェクトでの適用**: レポート作成関数はメール送信関数を直接呼び出さず、SQSというメッセージキューを介して連携する(要件6)。これにより、メール送信側の障害がレポート作成側の処理に影響しない。

## 略語・頭字語

### JST

**正式名称**: Japan Standard Time(日本標準時)

**本プロジェクトでの使用**: EventBridge Schedulerの実行時刻(毎月1日9:00)の基準として使用。

### DLQ

**正式名称**: Dead Letter Queue

**本プロジェクトでの使用**: [DLQ(デッドレターキュー)](#dlqdead-letter-queueデッドレターキュー)を参照。

### ARN

**正式名称**: Amazon Resource Name

**意味**: AWSリソースを一意に識別する文字列(例: `arn:aws:s3:::sales-report-automation-source-xxxx`)。IAMポリシーで権限の対象リソースを指定する際に使用する。

### SSE-S3

**正式名称**: Server-Side Encryption with Amazon S3-Managed Keys

**意味**: S3が管理する鍵を使った、保存データのサーバーサイド暗号化方式。

**本プロジェクトでの使用**: 両方のS3バケットのデフォルト暗号化設定として使用。

### ESM

**正式名称**: ECMAScript Modules

**意味**: JavaScriptの標準モジュール形式(`import`/`export`構文)。

**本プロジェクトでの使用**: 3つのLambda関数すべてでESMを採用し、ハンドラーファイルは`index.mjs`とする([development-guidelines.md](./development-guidelines.md#モジュール形式)参照)。

### tsc(TypeScriptコンパイラ)

**正式名称**: TypeScript Compiler

**意味**: TypeScriptのソースコード(`.mts`)をJavaScript(`.mjs`)に変換するコマンド。

**本プロジェクトでの使用**: AWS Lambdaランタイムは TypeScript を直接実行できないため、`npm run build`(内部で`tsc`を実行)でコンパイルしたJavaScriptをLambdaコンソールに貼り付ける([development-guidelines.md](./development-guidelines.md#言語とビルドの方針)参照)。

## データモデル用語

### レポート通知メッセージ

**定義**: Lambda(レポート作成)がSQS(レポート通知キュー)に送信するメッセージのJSON構造。

**主要フィールド**:
- `reportBucket`: レポートファイルが保存されたS3バケット名
- `reportKey`: レポートファイルのS3オブジェクトキー
- `reportSummary`: メール本文に記載するレポート概要のテキスト
- `generatedAt`: レポート生成日時(ISO8601形式)

**関連ドキュメント**: [functional-design.md](./functional-design.md#レポート通知メッセージlambdaレポート作成-sqs-lambdaメール送信)

**設計上の注意**: メール宛先(`RECIPIENT_EMAILS`)はこのメッセージには含めず、Lambda(メール送信)側の環境変数で管理する(責務分離のため)。

## エラー・例外

### Step Functions実行失敗

**発生条件**: Lambda(売上集計)またはLambda(レポート作成)が例外をthrowした場合、そのステートの実行が失敗する。

**対処方法**: Step Functionsの実行履歴(コンソール)でエラー内容を確認し、原因(CSV不備など)を解消した上で再実行する。

**関連ドキュメント**: [functional-design.md](./functional-design.md#エラーハンドリング)

### メール送信失敗によるリトライ超過

**発生条件**: Lambda(メール送信)がSESへの送信でエラーをthrowし続け、SQSのmaxReceiveCount(3回)を超過した場合。

**対処方法**: メッセージがDLQへ自動移動する。運用担当者がDLQの内容を確認し、原因調査後に元のキューへ再投入する(`runbooks/dlq-reprocessing.md`参照)。

**関連ドキュメント**: [functional-design.md](./functional-design.md#異常フロー-メール送信失敗時のリトライとdlq退避)
