# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称
**売上レポート自動配信ワークフロー** - 月次売上レポートの自動集計・作成・配信システム

### プロダクトコンセプト
- **サーバーレスによる完全自動化**: 人手を介さず、毎月決まった時刻にレポートが完成し関係者に届く
- **疎結合な非同期処理**: メール送信は専用キューを介して行い、集計・レポート作成処理と分離する
- **失敗の可視化と再処理性**: メール送信に失敗してもメッセージを失わずDLQで保持し、後から確認・再送できる

### プロダクトビジョン
経理担当者が毎月手作業で行っていた売上データのダウンロード・集計・レポート作成・メール送付を、AWS上のサーバーレスワークフローで完全自動化する。担当者の稼働や不在に依存せず、毎月1日の朝には正確なレポートが関係者に届いている状態を実現し、ヒューマンエラーと属人化のリスクを排除する。

### 目的
- 売上レポート作成における手作業をゼロにする
- 担当者の不在によるレポート遅延をなくす
- 集計ロジックをコード化し、属人化を解消する
- 障害発生時にもメッセージを失わず、後から復旧できる仕組みを持つ

## ターゲットユーザー

### プライマリーペルソナ: 経理担当者
- 毎月1日に売上レポートを作成し関係者へ配布する業務を担当
- 現在はCSVダウンロード→Excel集計→レポート作成→メール送付を手作業で実施
- 出張や休暇で不在の月はレポート作成が遅れることがある
- 期待する解決策: 何もしなくても毎月自動でレポートが届く状態

### セカンダリーペルソナ: インフラエンジニア(構築・運用担当)
- このワークフローをAWS上に構築し、運用・保守する
- 障害時(メール送信失敗など)にDLQを確認し、原因調査・再処理を行う
- AWSの各サービス(EventBridge、Step Functions、Lambda、S3、SQS、SES)の役割と設定を理解しながら構築する立場

## 成功指標(KPI)

### プライマリーKPI
- 月次レポートの手動作成工数: 0時間/月(自動化により完全代替)
- レポート配信の遅延: 0件(毎月1日9:00 JSTに必ず配信開始)
- 集計エラー(誤集計によるレポート再送)件数: 0件/月

### セカンダリーKPI
- メール送信失敗時のリトライ成功率: 90%以上(3回のリトライ以内に正常配信)
- DLQに滞留したメッセージの検知から再処理までのリードタイム: 1営業日以内

## 機能要件

### コア機能(MVP)

#### 機能1: 売上データの配置(要件1)

**ユーザーストーリー**:
経理担当者として、集計処理の入力データを用意するために、売上データ(CSV)をストレージに配置したい

**受け入れ条件**:
- [ ] S3バケットに売上CSVファイルを配置できる
- [ ] 配置は手動アップロード(AWSマネジメントコンソール操作)で行う

**優先度**: P0(必須)

#### 機能2: スケジュール実行(要件2)

**ユーザーストーリー**:
経理担当者として、手作業でワークフローを起動しなくて済むように、毎月決まった日時に自動でワークフローが開始されてほしい

**受け入れ条件**:
- [ ] 毎月1日 9:00(JST)にEventBridge Schedulerがトリガーされる
- [ ] トリガーによりStep Functionsのステートマシン実行が自動的に開始される

**優先度**: P0(必須)

#### 機能3: ワークフロー構築(要件3)

**ユーザーストーリー**:
インフラエンジニアとして、複数の処理を正しい順序で確実に実行するために、ワークフロー(ステートマシン)を構築したい

**受け入れ条件**:
- [ ] Step Functionsで「売上集計→レポート作成」の順に実行するステートマシンが定義されている
- [ ] 各ステップの実行結果(成功/失敗)が確認できる

**優先度**: P0(必須)

#### 機能4: 売上データ集計関数(要件4)

**ユーザーストーリー**:
経理担当者として、正確な集計結果を得るために、売上データを自動集計する関数が欲しい

**受け入れ条件**:
- [ ] Lambda関数がS3(売上CSV)からファイルを読み込む
- [ ] 商品カテゴリ別の売上合計が集計される
- [ ] 日別の売上合計が集計される
- [ ] 総売上金額が集計される
- [ ] 集計結果を後続のレポート作成処理に渡す

**優先度**: P0(必須)

**売上CSVフォーマット**(ユーザー提供サンプルに基づく):
```
date,product_id,product_name,category,quantity,unit_price,total_price
2024-01-01,P001,ノートPC,電子機器,5,80000,400000
2024-01-01,P002,マウス,電子機器,20,2000,40000
2024-01-01,P003,デスク,家具,3,25000,75000
```
集計には`date`列(日別合計)、`category`列(カテゴリ別合計)、`total_price`列(金額)を使用する。

**備考**: 具体的な集計軸・CSVフォーマットはユーザーが別途保有している仕様に基づき、詳細設計時に定義する

#### 機能5: レポート作成関数(要件5)

**ユーザーストーリー**:
経理担当者として、集計結果を人が読める形式で受け取るために、レポートを自動作成する関数が欲しい

**受け入れ条件**:
- [ ] Lambda関数が集計結果からレポートファイル(CSV形式)を生成する
- [ ] 生成したレポートをS3(レポート保存用バケット)に保存する
- [ ] レポート概要(メール本文に記載する要約情報)を後続処理に渡す

**優先度**: P0(必須)

#### 機能6: メッセージキューによる非同期連携(要件6)

**ユーザーストーリー**:
インフラエンジニアとして、レポート作成とメール送信の処理を疎結合にするために、メッセージキューを介した非同期連携を構築したい

**受け入れ条件**:
- [ ] レポート作成関数がSQS(レポート通知キュー)にメッセージを送信する
- [ ] キューにメッセージが入ると自動的にメール送信関数(Lambda)が起動する(イベントソースマッピング)

**優先度**: P0(必須)

#### 機能7: メール送信関数(要件7)

**ユーザーストーリー**:
経理担当者として、レポート内容をすぐに確認できるように、レポート概要をメールで受け取りたい

**受け入れ条件**:
- [ ] Lambda関数がキューのメッセージを受け取り、SESを使ってメールを送信する
- [ ] メール本文にレポートの概要が記載されている
- [ ] メール宛先は設定(環境変数など)で変更可能である
- [ ] SESはサンドボックスモードで運用し、送信元・宛先とも事前に検証済みのメールアドレスを使用する(検証用にユーザーのGmailアドレスを使用)

**優先度**: P0(必須)

#### 機能8: エラーハンドリング(要件8)

**ユーザーストーリー**:
インフラエンジニアとして、メール送信の一時的な失敗でメッセージを失わないように、リトライと退避の仕組みを構築したい

**受け入れ条件**:
- [ ] メール送信に失敗した場合、最大3回まで自動リトライされる(SQS Redrive Policy: maxReceiveCount = 3)
- [ ] 3回のリトライ後も失敗したメッセージはDLQ(SQS)に自動的に移動する
- [ ] DLQに移動したメッセージは削除されず保持され、後から内容を確認できる
- [ ] DLQのメッセージを再処理(元のキューへ再投入するなど)できる手順がある

**優先度**: P0(必須)

### 将来的な機能(Post-MVP)

#### POSシステム等からのCSV自動連携
現在は手動アップロードのみだが、将来的には販売管理システムからS3への自動転送を検討する

**優先度**: P2(できれば)

#### SES本番運用への移行
検証済みメールアドレスへの送信に限定せず、任意の宛先へ送信できるよう本番アクセスをリクエストする

**優先度**: P2(できれば)

## 非機能要件

### 信頼性
- メール送信失敗時、最大3回のリトライを行う
- リトライ上限を超えたメッセージはDLQで永続的に保持し、消失しない
- Step Functionsの各ステップの実行履歴が確認できる(実行が失敗した場合も記録が残る)

### 運用性
- DLQに滞留したメッセージの有無を確認できる(MVPでは手動確認。将来的にCloudWatchアラームでの通知を検討)
- 各AWSリソースの設定内容がドキュメント(`docs/architecture.md`)として残されている

### セキュリティ
- 各Lambda関数のIAMロールは必要最小限の権限(対象S3バケットのみ、対象SQSキューのみなど)に限定する
- SESは検証済みメールアドレスのみに送信を許可するサンドボックスモードで運用する

### スケーラビリティ
- 月次バッチ実行が前提であり、同時実行数やスループットの高い要件はない(小売企業1社分の月次データ量を想定)

## スコープ外

明示的にスコープ外とする項目:
- 売上CSVの自動アップロード(POS/基幹システムとの連携)
- SESの本番アクセス申請(サンドボックスのままで運用)
- 複数店舗・複数事業部に対する権限分岐やアクセス制御
- ダッシュボードなどの可視化UI
- IaC(Terraform/CDK等)によるコード化(今回はAWSマネジメントコンソールでの手動構築)
